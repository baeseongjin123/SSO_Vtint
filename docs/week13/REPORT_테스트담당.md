## 2. 12주차 오탐 4건 원인 (재현·확인)
Docker `vtint-env`에서 12주차와 같은 결과(64개 중 실패 4)를 재현한 뒤 `nm`, `objdump`, `readelf`, gdb로 확인했다.

| 테스트 | 확인한 사실 | 원인 |
|---|---|---|
| E2 `multi_base2` | Multi 생성자 `mov $0x402060`(1차)은 0x500018로 패치됨, `mov $0x402090`(2차)은 그대로 | ELFParser가 offset-to-top ≠ 0에서 vtable 그룹을 끊어 2차 주소점이 패치 목록에 없음 |
| E5 `first`, `all` | vtable 201개 중 154개가 vtsec 둘째 페이지 이후, `Big<0>` → 0x504470 | ID를 vtsec 첫 페이지에만 기록 |
| C14 `big_maps` | `region=[unmapped]` | 검사 루틴이 maps를 64KB까지만 읽음 |

## 3. 추가 검증 사례
`tests/week13/w13_main.cpp` 한 프로그램에 모드 32개를 넣고, 빌드 옵션 3종(B1~B3)을 더했다. 세 묶음으로 나눴다.

- **N (정상, 19개)**: 보호 후에도 출력이 같고 탐지가 없어야 한다. 슬롯 번호, 인자 개수, 다중·가상 상속, 추상 클래스, 전역 객체, 라이브러리 객체, 스레드, fork, 작은 스택, fd 고갈, 매핑 3000개.
- **K (계측 범위, 11개)**: vptr을 진짜 vtable의 사본으로 바꿔 호출한다. 보호 전에는 정상이고, 보호 후 탐지되지 않으면 그 형태의 호출에는 검사가 없다는 뜻이다. 공격 함수 없이 보호 범위를 하나씩 확인하려고 만든 방식이다.
- **L (원논문 한계, 2개)**: 다른 진짜 vtable 재사용. 탐지되지 않는 것을 기대값으로 둔다.

실행 결과(2026-11-24): **전체 99개 중 79개 통과, 20개 실패** (12주차 실패 4 + 새 테스트 35개 중 실패 16). 고정 사례 3종과 tc1~tc3은 모두 통과했다.

| C13 | PIE 입력에 깨진 바이너리 출력 | 명세상 미지원 (+거부 처리 요청) |

가장 중요한 발견은 두 가지다.
- **C6**: 지금 구현은 slot 0 가상 호출에만 검사를 넣는다. 고정 사례가 모두 slot 0이라 12주차에는 드러나지 않았다.
- **C1·C2**: 보호가 정상 프로그램을 크래시시킨다. 오탐보다 심각하다.

## 6. 남은 한계 (수정하지 않을 것)
- **vtable 재사용(C14)**: 원논문 한계. 읽기 전용이고 ID가 맞는 진짜 vtable이면 통과한다.
- **검사와 호출 사이의 경쟁(TOCTOU)**: 검사 뒤 다른 스레드가 vptr을 바꾸는 경우. 원논문 구조도 같아서 시험하지 않고 한계로만 적는다.
- **지원 범위**: PIE, 최적화 빌드, 여러 모듈. 거부 처리만 넣고 지원은 범위 밖으로 둔다(구현 담당 판단).

## 8. AI 활용 기록
- **요청**: 12주차 오탐 원인 분석, 반례 후보 발굴, 테스트 프로그램과 pytest 작성, 구현 담당용 문서 정리 (Claude Code 사용)
- **확인 방법**: 모든 결과를 Docker 컨테이너에서 직접 실행해 얻었다. 원인 설명은 `nm`, `objdump`, gdb 출력(주소, 명령, 크래시 지점)과 맞춰 보았다. 문서의 주소와 메시지는 저장된 로그(`docs/results/week13/logs/`)에서 확인할 수 있다.
- **채택·수정**: 테스트 프로그램과 기대값 표는 그대로 채택했다. 원인을 확인하려고 AI가 BitCover를 시험 수정한 결과(C3, C11 발견)는 저장소에 넣지 않고 근거로만 썼다. 원논문 절 번호는 AI 기억에 의존하지 않고 원문으로 다시 확인하기로 했다.
- **어려웠던 점**: slot 1 문제를 고치면 숨어 있던 다른 반례(C3, C11)가 드러나는 의존 관계가 있었다. 그래서 문서에 "함께 고칠 것"과 수정 순서를 따로 적었다.

> 위 AI 기록은 초안이다. 실제로 직접 확인한 부분(예: 직접 다시 돌려 본 테스트)은 본인이 고쳐 쓴다.
